# ORB — OCI Registry Benchmark: Requirements

This document is the source of truth for what ORB must do. It is written for
both human contributors and AI coding assistants. Every design decision and
every change to the code must be consistent with it. If a requirement needs to
change, update this document first, in the same change as the code.

Keywords **MUST**, **SHOULD** and **MAY** are used as in RFC 2119.
Each requirement has an ID (for example `LAT-2`) so it can be referenced in
code reviews, issues and commit messages.

---

## 1. Purpose and scope

ORB benchmarks OCI container registries that we operate ourselves. It measures
latency and throughput of registry operations under controlled, repeatable load
generated by many simultaneous simulated clients.

- **SCOPE-1** The primary target is **Harbor**. All features MUST work against Harbor.
- **SCOPE-2** ORB SHOULD also work against other OCI Distribution–compliant
  registries, including AWS ECR, Azure ACR and Google Artifact Registry / GCR.
- **SCOPE-3** ORB is meant for benchmarking our own installations, not for
  load testing public cloud registry services. The design target is
  **hundreds** of simultaneous workers per run, not tens of thousands.
- **SCOPE-4** ORB runs inside Kubernetes as an operator. Users control it with
  the CLI `orbctl`.

---

## 2. Terminology

| Term | Meaning |
|---|---|
| **Worker** | One simulated registry client. It runs registry operations one after another, in a loop. |
| **Agent** | A pod that runs many workers. |
| **Operation** | One registry action, such as a pull, a push or a tag listing. |
| **Benchmark** | A reusable, named definition of a test (`OrbBenchmark`). |
| **Scenario** | One sub-benchmark inside a benchmark. Each scenario has a type, such as `load` or `deduplication`. |
| **Run** | One execution of a benchmark (`OrbBenchmarkRun`). |
| **Result** | The measured outcome of one run (`OrbBenchmarkResult` plus detail data in SQLite). |
| **Stage** | One segment of a load profile, with a duration and a target worker count. |
| **Image set** | The images used as test data: either randomly generated or a fixed static list. |
| **Registry module** | A Go package that holds the special handling one specific registry needs, such as `harbor` or `ecr`. |

## 3. Architecture requirements

- **ARCH-1** ORB MUST be built as a Kubernetes operator with Custom Resource
  Definitions (CRDs). The Kubernetes API is the control plane for starting,
  stopping and inspecting benchmarks.
- **ARCH-2** ORB MUST define these three CRDs:
  - `OrbBenchmark`: a reusable benchmark definition (registry, auth, image set,
    scenarios, load profiles, cleanup).
  - `OrbBenchmarkRun`: one execution of an `OrbBenchmark`.
  - `OrbBenchmarkResult`: the summary results of one run.
- **ARCH-3** The CRDs MUST use the API group **`orb.kubectl.dk`**, starting at
  version `v1alpha1` (for example `orb.kubectl.dk/v1alpha1`).
- **ARCH-4** The **orb-controller** MUST reconcile `OrbBenchmarkRun` objects:
  start agents, coordinate stages, collect metrics, write results, and clean up.
- **ARCH-5** Agents MUST run as a Kubernetes **Indexed Job**, one Job per run,
  so each agent pod knows its index and is cleaned up when the run ends.
- **ARCH-6** Agents MUST report metrics to the controller while the run is in
  progress, at least once per measurement interval (default 1 second).
- **ARCH-7** ORB MUST be installable with a Helm chart that includes the CRDs,
  the controller Deployment, its PersistentVolumeClaim (for SQLite, see
  section 11), RBAC and default agent settings.
- **ARCH-8** ORB MUST run one controller replica, which MUST be able to handle
  the scale in SCOPE-3. Because the SQLite database lives on a single volume,
  the Deployment MUST use the `Recreate` strategy, and leader election MUST be
  enabled so that two controllers never write at the same time.

## 4. Reusable benchmarks and runs

- **RUN-1** An `OrbBenchmark` MUST fully describe a test, so the same test can
  be run again at any time with identical settings.
- **RUN-2** Starting a benchmark MUST create a new `OrbBenchmarkRun` that refers
  to an `OrbBenchmark` by name. Running the same benchmark again creates another
  run. Earlier runs and their results are kept.
- **RUN-3** When a run starts, the controller MUST copy the complete benchmark
  spec into the run's status. Later edits to the `OrbBenchmark` MUST NOT change
  what an existing run did or how its results are interpreted.
- **RUN-4** An `OrbBenchmarkRun` MAY override selected fields of the benchmark,
  such as a load profile, the target repository or the cleanup policy.
  Overrides MUST also be recorded in the run's status.
- **RUN-5** A run MUST move through clear phases, shown in its status:
  `Pending → Preparing → Seeding → Running → Collecting → CleaningUp → Succeeded | Failed | Aborted`.
  While `Running`, the status MUST also show which scenario is active.
- **RUN-6** A user MUST be able to abort a running run. Agents MUST stop
  quickly, and the results gathered so far MUST still be written, marked as
  aborted.
- **RUN-7** Random workloads MUST accept a seed, so the same sequence of sizes
  and operations can be reproduced.

### 4.1 Cleanup

- **CLEAN-1** The cleanup policy MUST be an option in the `OrbBenchmark` spec,
  with the values `Delete` (remove everything the run pushed) and `Keep`.
  The default is `Delete`.
- **CLEAN-2** Cleanup MUST run after all scenarios have finished, in the
  `CleaningUp` phase, and MUST NOT be counted in the results.
- **CLEAN-3** Cleanup MUST only remove artifacts in the run's own repository
  namespace (IMG-12). It MUST NOT touch anything else in the registry.
- **CLEAN-4** How artifacts are deleted is registry-specific (for example the
  Harbor API versus a plain manifest `DELETE`), so it MUST be implemented in the
  registry modules (section 12). If a registry does not allow deletion, the run
  MUST still succeed and report that cleanup was not possible.
- **CLEAN-5** ORB MUST NOT trigger registry garbage collection. That is left to
  the people who operate the registry.

## 5. Benchmark types (scenarios)

A benchmark is made of one or more scenarios. Each scenario is a sub-benchmark
of a specific type. New types will be added over time, so the structure must
make that easy.

- **TYPE-1** An `OrbBenchmark` MUST contain a list of scenarios. Each scenario
  has a name, a type, its own settings and its own load profile (section 10).
- **TYPE-2** Scenarios in a run MUST run one after another, in the order they
  are listed, so they do not affect each other's measurements.
- **TYPE-3** Results MUST be reported per scenario.
- **TYPE-4** Each scenario type MUST be implemented as its own Go package
  behind a common interface (for example: validate, prepare, seed, run one
  worker iteration, clean up). Adding a new type MUST NOT require changes to
  the code of other types.
- **TYPE-5** The CRD MUST reject unknown scenario types when the object is
  created.
- **TYPE-6** The first version MUST include these types:
  - `load`: a general load test with a configurable mix of operations
    (section 7).
  - `deduplication`: measures how fast the registry handles pushes of content
    it already has (section 5.1).

### 5.1 Deduplication scenario

- **DEDUP-1** The `deduplication` scenario MUST measure how quickly the
  registry handles pushes of blobs that already exist in the registry.
- **DEDUP-2** The blobs that will be pushed again MUST be uploaded during
  seeding, which is not measured.
- **DEDUP-3** Where the existing blobs live MUST be configurable, and ORB MUST
  support these scopes:
  - the same repository,
  - another repository in the same project or namespace,
  - a repository in a different project or namespace.
- **DEDUP-4** These push methods MUST be supported, and one or more can be
  selected per scenario:
  - `existenceCheck`: the client sends `HEAD` for each blob and skips the
    upload when the registry answers that the blob exists, like Docker and
    containerd do. Then it pushes the manifest.
  - `crossRepoMount`: the client asks the registry to mount the blob from
    another repository (`POST /v2/<name>/blobs/uploads/?mount=<digest>&from=<repo>`).
  - `reupload`: the client uploads the full data again, to measure whether the
    registry finishes faster when it already has the content.
- **DEDUP-5** Latency for a deduplicated push MUST be measured from the start of
  the push until the registry accepts the manifest `PUT`. The time of the
  deduplication step for each blob (the `HEAD` response, the mount response, or
  the final upload `PUT`) MUST also be recorded.
- **DEDUP-6** If a mount request does not mount the blob (the registry answers
  `202 Accepted` and starts a normal upload), ORB MUST count it as a
  **mount miss**, report it separately, and finish the push with a normal upload.
- **DEDUP-7** The scenario SHOULD also push the same image sizes with unique
  content, as a baseline, so results can show how much faster deduplication is.

## 6. Image sets (test data)

ORB supports two kinds of test data.

### 6.1 Random image set

- **IMG-1** ORB MUST be able to generate random images: a configurable number of
  layers and layer sizes (a fixed size, a uniform range, or a list of sizes).
- **IMG-2** Random data MUST NOT compress well, so registry or network
  compression does not distort throughput.
- **IMG-3** Random data MUST be generated as a stream and uploaded directly,
  with the digest computed on the fly. Agents MUST NOT need local disk space in
  proportion to the data they push.
- **IMG-4** Outside the `deduplication` scenario, every push MUST use unique
  blobs by default, so the registry cannot skip uploads through deduplication
  or cross-repository blob mounts.

### 6.2 Static image set

- **IMG-5** ORB MUST support a fixed list of real container images, given as
  image references (tag or digest), as the test data.
- **IMG-6** Before measuring starts, each agent MUST download every image in the
  static set into local storage on the agent (memory or an `emptyDir` volume).
  This download is preparation only and MUST NOT be included in any measurement.
- **IMG-7** The static set MAY be pulled from a registry other than the one
  being tested. Separate credentials MUST be possible for the source registry.
- **IMG-8** Images in a static set SHOULD be pinned by digest so that every run
  uses identical data. If a tag is used, the resolved digest MUST be recorded in
  the run status.
- **IMG-9** The agent's local storage MUST have a configurable size limit. The
  run MUST fail with a clear error during `Preparing` if the static set does not
  fit.

### 6.3 Seeding for pull tests

- **IMG-10** Pull, HEAD, tag, tag-list and deduplication operations need
  content that already exists in the target registry. The controller MUST run a
  **seeding** step before the measurement starts that pushes the needed images
  (random or static) to the target. Seeding MUST NOT be included in any
  measurement.
- **IMG-11** Pull workers MUST pick images from the seeded pool so that load is
  spread across many images, not one cached blob. The selection strategy
  (random or round-robin) MUST be configurable.

### 6.4 Repository layout

- **IMG-12** Each run MUST push into its own repository namespace (for example a
  path that includes the run name), so runs do not interfere with each other.

## 7. Operations to benchmark

The `load` scenario selects which operations to run and in what proportions (a
mix in percent). All of these MUST be supported:

| ID | Operation | OCI Distribution API calls |
|---|---|---|
| **OP-1** | Pull image | `GET` manifest, then `GET` each blob |
| **OP-2** | Push image | `POST` upload session, chunked `PATCH`, final `PUT` per blob, then `PUT` manifest |
| **OP-3** | HEAD manifest | `HEAD /v2/<name>/manifests/<ref>` |
| **OP-4** | HEAD blob | `HEAD /v2/<name>/blobs/<digest>` |
| **OP-5** | Tag image | `PUT` an existing manifest under a new tag |
| **OP-6** | List tags | `GET /v2/<name>/tags/list`, following pagination |
| **OP-7** | Catalog | `GET /v2/_catalog`, following pagination |

- **OP-8** In the `load` scenario, push MUST always send the data. It MUST NOT
  skip a blob upload because a `HEAD` shows the blob already exists. (Skipping
  and mounting are measured by the `deduplication` scenario.)
- **OP-9** The chunk size for pushes MUST be configurable.
- **OP-10** Pulled data MUST be read in full and thrown away (or checked
  against its digest if verification is turned on). It MUST NOT be written to
  disk.
- **OP-11** Pagination page size for tag listing and catalog MUST be
  configurable, and results MUST record how many pages were fetched.

## 8. Latency measurement

- **LAT-1** Latency MUST be measured with a monotonic clock from the moment the
  worker **starts** the operation, including any auth token request it needs.
- **LAT-2** **Pull latency** ends when the **first byte of the first blob body
  is received** from the registry.
- **LAT-3** **Push latency** ends when the registry **acknowledges the first
  chunk**, meaning the `202 Accepted` response to the first `PATCH` of the
  first blob.
- **LAT-4** For HEAD, tag listing and catalog operations, latency ends when the
  **first byte of the response** is received. For catalog and tag listing, the
  total time for all pages MUST also be recorded.
- **LAT-5** For tagging, latency ends when the response to the manifest `PUT`
  is received.
- **LAT-6** Each operation MUST also record its phases where they apply: DNS
  lookup, TCP connect, TLS handshake, auth token request, manifest request,
  upload session creation and time to first byte. The phases show where the
  time goes.
- **LAT-7** ORB MUST use its own small OCI Distribution client built on Go's
  `net/http` and `httptrace`, so that these timestamps are exact. Third-party
  libraries MAY be used for auth, but not in the measured data path.

Latency for the `deduplication` scenario is defined in DEDUP-5.

---

## 9. Throughput measurement

- **THR-1** Per-operation throughput MUST be calculated as bytes transferred
  divided by the time from the first byte to the last byte, so that latency
  does not lower the figure.
- **THR-2** Aggregate throughput (bytes per second across all workers) MUST be
  reported per measurement interval, for push and pull separately.
- **THR-3** The rate of operations per second MUST be reported per operation
  type and per interval.

---

## 10. Load generation

- **LOAD-1** Each scenario's load profile MUST be a list of stages. Each stage
  has a duration and a target worker count. Worker counts change linearly
  within a stage (ramp up, hold, ramp down).
- **LOAD-2** The controller MUST work out the number of agents from the highest
  worker count in any scenario and a configurable maximum number of workers per
  agent.
- **LOAD-3** Agents MUST start each scenario's stage plan at a shared start time
  set by the controller, so all agents ramp in step.
- **LOAD-4** Each worker MUST behave as an independent client with its own HTTP
  client. Connection reuse MUST be configurable: reuse connections per worker,
  or open a new connection for every operation (cold client).
- **LOAD-5** A warm-up period MAY be defined. Measurements taken during warm-up
  MUST be kept separate from the main results.
- **LOAD-6** An optional think time between operations per worker MUST be
  configurable (default: none).
- **LOAD-7** Per-operation and overall timeouts MUST be configurable.
- **LOAD-8** Agents MUST be spread across nodes by default (pod anti-affinity
  or topology spread), so that one node's network does not limit the test.
- **LOAD-9** Agents MUST report their own CPU usage and scheduling delay. If the
  agents were the bottleneck, the result MUST be flagged, so that a slow client
  is not mistaken for a slow registry.

## 11. Results and storage

Results are stored in two places: a compact summary in the `OrbBenchmarkResult`
CRD, and the full detail in a SQLite database owned by the controller.

### 11.1 Summary: `OrbBenchmarkResult`

- **RES-1** Each run MUST have an `OrbBenchmarkResult` object, owned by its
  `OrbBenchmarkRun`.
- **RES-2** Agents MUST record latency in HDR histograms. The controller MUST
  merge histograms from all agents, so that percentiles are correct across the
  whole run (averaging percentiles is not allowed).
- **RES-3** For each scenario and operation type, the summary MUST include:
  operation count, error count by type (HTTP status, timeout, connection
  error), latency min/p50/p90/p95/p99/p99.9/max, and throughput (for push and
  pull). Deduplication scenarios MUST also include mount misses (DEDUP-6) and
  the baseline comparison (DEDUP-7).
- **RES-4** The summary MUST include figures per stage and a coarse time series
  of the key figures (worker count, operations per second, p50, p99, bytes per
  second, errors).
- **RES-5** A Kubernetes object is limited in size (about 1.5 MiB in etcd). The
  summary MUST stay well under this limit. The time series in the CRD MUST be
  reduced to a coarser interval when needed. The full-resolution data lives in
  SQLite.
- **RES-6** The summary MUST include the context needed to compare runs: the
  benchmark spec snapshot, image digests, agent count, the registry address,
  registry module and version (if the registry reports it), and the saturation
  flag from LOAD-9.
- **RES-7** The summary MUST include a reference to the run's detail data in
  SQLite (for example the run's UID).

### 11.2 Detail: SQLite

- **RES-8** The controller MUST store the detailed results in a SQLite
  database on a PersistentVolume, using the driver
  `github.com/mattn/go-sqlite3` (see section 15 for the license exception). The detail data MUST include, per
  measurement interval: merged histograms per scenario and operation type,
  phase breakdowns (LAT-6), per-agent figures, and error counts with example
  error messages.
- **RES-9** Raw per-operation samples MAY also be stored in SQLite. This MUST be
  off by default.
- **RES-10** Only the controller MUST read and write the database. Agents send
  their data to the controller (ARCH-6) and never access the database directly.
- **RES-11** The database schema MUST be versioned, with migrations that run
  automatically when the controller starts.
- **RES-12** When an `OrbBenchmarkRun` is deleted, its detail data MUST also be
  deleted (using a finalizer).

### 11.3 Export

- **RES-13** The controller MUST provide a read-only export endpoint for detail
  data on an in-cluster Service. `orbctl` MUST reach it through the Kubernetes
  API (service proxy or port-forward) with the user's kubeconfig, so access is
  still controlled by Kubernetes RBAC.
- **RES-14** `orbctl result export` MUST combine the `OrbBenchmarkResult`
  summary with the SQLite detail data into one export, in these formats:
  - `json`: one document with summary and detail,
  - `csv`: one file per table (for example time series, phases, errors),
  - `sqlite`: a standalone database file holding only that run.
- **RES-15** The controller SHOULD expose live metrics in Prometheus format
  while a run is in progress.

## 12. Registry support: common core and registry modules

ORB talks to all registries through one common OCI code path. Anything that
only one registry needs lives in a separate module named after that registry.

- **REG-1** ORB MUST have a common **core** package that implements the OCI
  Distribution specification and is used for every registry. All measured
  operations MUST go through it (LAT-7).
- **REG-2** The core MUST NOT contain code for specific registries. There MUST
  be no checks such as "if this is Harbor" in the core.
- **REG-3** Behaviour needed only by a specific registry MUST live in a
  separate package per registry, and the package name MUST be the registry's
  name. The first modules are:
  - `harbor`: Harbor (primary target, MUST be implemented first),
  - `ecr`: AWS Elastic Container Registry,
  - `acr`: Azure Container Registry,
  - `gar`: Google Artifact Registry, including legacy GCR.
- **REG-4** Registry modules MUST implement one common Go interface. Each hook
  in the interface MUST have a generic default from the core, so a module only
  implements what its registry does differently. Hooks include:
  - authentication (section 13),
  - preparing repositories before a run (for example creating ECR repositories
    or checking that a Harbor project exists),
  - deleting artifacts for cleanup (CLEAN-4),
  - which operations are supported (for example a registry without
    `/v2/_catalog`),
  - registry limits such as allowed chunk sizes,
  - detecting the registry version (for example from Harbor's system info API).
- **REG-5** Registries without special needs MUST work with a `generic` module,
  which uses only the core defaults.
- **REG-6** The registry module MUST be chosen in the `OrbBenchmark` spec (for
  example `registry.module: harbor`). The default is `generic`. ORB MAY detect
  the registry automatically, but an explicit choice always wins.
- **REG-7** If a scenario uses an operation the chosen registry does not
  support, the run MUST fail during `Preparing` with a clear message, and
  `orbctl registry check` MUST report it. Unsupported operations MUST NOT be
  counted as errors during a run.
- **REG-8** Hooks that run inside a measured operation (such as fetching an
  auth token) MUST be timed as their own phase (LAT-6), so registry-specific
  code is visible in the results.

## 13. Authentication

- **AUTH-1** Authentication MUST be built as pluggable providers behind one
  common interface.
- **AUTH-2** The core MUST provide these generic providers, which Harbor uses:
  - **Basic auth / Docker config:** credentials from a Kubernetes Secret of type
    `kubernetes.io/dockerconfigjson`. This includes Harbor users and Harbor
    robot accounts.
  - **Bearer token flow:** the standard registry token flow
    (`WWW-Authenticate` challenge, then token request).
- **AUTH-3** These registry-specific providers SHOULD exist, each in its own
  registry module (REG-3):
  - `ecr`: token from `GetAuthorizationToken`, using IRSA / EKS Pod Identity or
    static credentials.
  - `acr`: Microsoft Entra ID token exchanged for an ACR token, using Workload
    Identity or a service principal. The ACR admin user works through basic
    auth.
  - `gar`: OAuth2 access token, using Workload Identity or a service account
    key.
- **AUTH-4** Tokens MUST be cached and refreshed per worker, the way a real
  client would. Token requests MUST be visible as their own phase (LAT-6).
- **AUTH-5** Custom CA certificates MUST be supported. Skipping TLS
  verification MAY be supported for test installations and MUST be off by
  default.
- **AUTH-6** Secrets MUST NOT appear in logs, CRD status, results, the SQLite
  database or `orbctl` output.

## 14. orbctl (CLI)

- **CLI-1** `orbctl` MUST talk to the Kubernetes API using the user's
  kubeconfig. Access is controlled by Kubernetes RBAC.
- **CLI-2** `orbctl` MUST support at least:

  ```
  orbctl benchmark apply -f benchmark.yaml
  orbctl benchmark list
  orbctl benchmark get <name>
  orbctl benchmark delete <name>

  orbctl run start <benchmark> [--set key=value ...] [--watch]
  orbctl run list [--benchmark <name>]
  orbctl run status <run>
  orbctl run watch <run>        # live view: scenario, workers, ops/s, p50/p99, MB/s, errors
  orbctl run abort <run>

  orbctl result get <run> -o table|json|yaml
  orbctl result export <run> -o json|csv|sqlite --output <path>
  orbctl result compare <run-a> <run-b>

  orbctl registry check <benchmark>   # check auth, connectivity and supported operations, no load
  ```

- **CLI-3** Everything `orbctl` does with benchmarks, runs and summaries MUST
  also be possible with `kubectl` and plain YAML. Detail data MUST be reachable
  with `kubectl port-forward` and a plain HTTP client. `orbctl` is a
  convenience, not a requirement.
- **CLI-4** Output MUST be readable by humans by default and machine-readable
  (JSON or YAML) on request.

## 17. Engineering requirements

- **ENG-1** All code MUST be written in **Go**.
- **ENG-2** Code MUST be easy for humans to read: clear names, simple control
  flow, and comments where the intent is not obvious.
- **ENG-3** Code MUST be organized into small, focused packages (modules).
- **ENG-4** No file SHOULD be longer than about **1000 lines**. Split files or
  packages before they grow beyond that.
- **ENG-5** The binaries are `orbctl` (CLI) and `orb` (one image with
  `controller` and `agent` subcommands).
- **ENG-6** The operator SHOULD be built with `controller-runtime` (kubebuilder
  conventions) and the CLI with `cobra`.
- **ENG-7** Measurement code (latency, throughput, histograms) MUST have unit
  tests.
- **ENG-8** There SHOULD be an end-to-end test that runs ORB in a local
  cluster (for example `kind`) against a local registry.
- **ENG-9** The package layout SHOULD follow this structure, so the separations
  required above (TYPE-4, REG-1 to REG-3) are visible in the code:

  ```
  cmd/orbctl/                  CLI entry point
  cmd/orb/                     controller and agent entry point
  api/v1alpha1/                CRD types (orb.kubectl.dk)
  internal/registry/core/      common OCI Distribution client and timing
  internal/registry/harbor/    Harbor-specific handling
  internal/registry/ecr/       ECR-specific handling
  internal/registry/acr/       ACR-specific handling
  internal/registry/gar/       Artifact Registry / GCR-specific handling
  internal/registry/generic/   default module, core behaviour only
  internal/scenario/load/      load scenario type
  internal/scenario/dedup/     deduplication scenario type
  internal/imageset/           random and static image sets
  internal/loadprofile/        stages and ramping
  internal/metrics/            histograms, intervals, merging
  internal/agent/              worker pool and reporting
  internal/controller/         reconcilers and run lifecycle
  internal/store/              SQLite storage and migrations
  internal/export/             export endpoint and formats
  internal/cli/                orbctl commands and output
  ```

## 18. Repository, build and release

- **BUILD-1** The source code MUST be hosted on GitHub at
  `github.com/zensonic/oci-reg-benchmark`. This is also the Go module path.
- **BUILD-2** All builds, tests and releases MUST run in **GitHub Actions**.
- **BUILD-3** Every pull request and every push to `main` MUST run the CI
  workflow: tidy check, `go vet`, unit tests with the race detector, build,
  golangci-lint, license checks (LIC-3, LIC-5), a multi-arch image build
  without pushing, and `helm lint` once the chart exists.
- **BUILD-4** Developers MUST be able to run the same checks locally with
  `make ci`. Workflows SHOULD call Makefile targets rather than repeat the
  commands.
- **BUILD-5** All GitHub Actions MUST be pinned to a full commit SHA, with the
  version in a comment. Workflows MUST use least-privilege `permissions`
  (read-only by default, write only in the jobs that need it) and MUST NOT
  persist checkout credentials.
- **BUILD-6** Releases MUST be triggered by pushing a Semantic Versioning tag
  (`vMAJOR.MINOR.PATCH`). Tags with a pre-release suffix MUST be published as
  pre-releases and MUST NOT move the `latest` image tag.
- **BUILD-7** The `orb` image MUST be published to
  `ghcr.io/zensonic/oci-reg-benchmark/orb` for `linux/amd64` and `linux/arm64`,
  built on a minimal, non-root base image with base images pinned by digest.
  Because the SQLite driver needs CGO (RES-8), the `orb` binary MUST be built
  with CGO and linked statically, so it still runs on a distroless static base
  image.
- **BUILD-8** The Helm chart MUST be published as an OCI artifact to
  `oci://ghcr.io/zensonic/oci-reg-benchmark/charts/orb`, with the chart version
  and app version equal to the release version.
- **BUILD-9** `orbctl` MUST be released as archives for Linux, macOS and
  Windows on amd64 and arm64, with a checksum file, using GoReleaser.
- **BUILD-10** All release artifacts (archives, image and chart) MUST be signed
  keyless with Sigstore cosign, MUST have an SBOM, and MUST have SLSA build
  provenance attestations.
- **BUILD-11** Dependabot MUST keep Go modules, GitHub Actions and base images
  up to date. CodeQL MUST scan the Go code and the workflows. OpenSSF Scorecard
  MUST run on `main`.
- **BUILD-12** The repository MUST include the standard community files:
  `README.md`, `LICENSE`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`,
  `SECURITY.md`, `MAINTAINERS.md`, `RELEASING.md`, `CODEOWNERS`, and templates
  for issues and pull requests.
